# LLM Judge: как мы научили AI оценивать свой же контент

Реализовали систему автоматической оценки качества для образовательной платформы. Генерация контента уроков через LLM — это круто, но есть две ключевые проблемы:

1. **Как понять, что контент качественный?**
2. **Как бороться с галлюцинациями?**

Человеческая проверка каждого урока — дорого и медленно. LLM-оценка — быстро, но есть нюансы.

---

## Проблема: Self-Evaluation Bias

Модель оценивает свой контент на **10-25% выше** чужого. Это не баг — это особенность LLM.

**Решение: Cross-Model Judging**

Судьи ВСЕГДА отличаются от генератора:
- RU контент (Qwen3) → судят DeepSeek, Kimi K2, Minimax M2
- EN контент (DeepSeek) → судят Qwen3, Kimi K2, Minimax M2

Никакого "сам себя похвалил".

---

## Проблема: 3 судьи = дорого

Классический подход: запустить 3 LLM, взять медиану. Работает, но каждый вызов стоит денег.

**Решение: CLEV Voting**
(Consensus via Lightweight Efficient Voting)

Алгоритм:
1. Запускаем 2 судей параллельно
2. Если оценки близки (разница < 10%) → сразу возвращаем результат
3. Если расхождение → запускаем 3-го как tiebreaker

В 67% случаев 2 судей достаточно. Экономия ~33% на оценке.

---

## Что оцениваем: OSCQR Rubric

6 критериев для образовательного контента:

```
Objective Alignment   25%  — соответствие целям обучения
Pedagogical Structure 20%  — правильная последовательность
Factual Accuracy      15%  — отсутствие ошибок
Clarity               15%  — понятность языка
Engagement            15%  — примеры, интерактивность
Completeness          10%  — полнота раскрытия темы
```

Веса подобраны на основе исследований эффективности онлайн-обучения.

---

## Decision Tree: что делать с оценкой

Не просто "хорошо/плохо", а конкретные действия:

```
Score >= 90%  → ACCEPT (публикация)
75-90%        → TARGETED_FIX (точечное исправление)
60-75%        → ITERATIVE_REFINEMENT (до 2 итераций)
< 60%         → REGENERATE (полная перегенерация)
```

Каждое решение — конкретное действие пайплайна.

---

## Когда эскалируем к человеку

6 триггеров автоматической эскалации:

1. Score < 75% после 2 итераций фиксов
2. Все судьи неуверены в своей оценке
3. Судьи сильно разошлись во мнениях (> 20%)
4. Критические ошибки в фактах
5. Стоимость превысила 5x базовой генерации
6. Достигнут максимум итераций

AI не должен бесконечно крутиться — если не справляется, зовем человека.

---

## Борьба с галлюцинациями

Одна из ключевых задач. LLM может уверенно выдавать неправильные факты — особенно опасно в образовательном контенте.

**Entropy Detection** — обнаружение галлюцинаций через logprob (log-probability токенов).

Как работает:
- Модель возвращает вероятности для каждого токена
- Высокая энтропия = модель "гадает" между вариантами
- Низкая уверенность в ответе = красный флаг

```
Низкая энтропия (< 0.3)  → уверенный ответ
Средняя (0.3-0.6)        → возможная неуверенность
Высокая (> 0.6)          → потенциальная галлюцинация
```

При высокой энтропии запускаем дополнительную верификацию через RAG — проверяем утверждения по исходным документам курса.

**Factual Accuracy в рубрике** — отдельный критерий с весом 15%. Критические ошибки в фактах → автоматическая эскалация к человеку с высоким приоритетом.

---

## Дополнительные оптимизации

**Heuristic Filter** — бесплатная проверка ДО вызова LLM:
- Длина текста в норме?
- Структура соответствует шаблону?
- Нет явных паттернов ошибок?

Отсеивает 15-20% очевидно плохого контента без затрат.

**Prompt Cache** — кеширование системных промптов. Один и тот же rubric не перечитываем каждый раз.

---

## Итого

```
Без оптимизаций:     3 LLM-вызова на каждый урок
С нашей системой:    ~2 вызова в среднем
                     + heuristic filter (бесплатно)
                     + entropy detection (почти бесплатно)
                     + prompt cache (экономия токенов)
```

Экономия ~30-40% на оценке качества при сохранении точности.
