# Тактический агентный кодинг: Builder + Validator, мета-промпты и самовалидация вместо вайбкодинга

*Подход IndyDevDan к организации AI-агентов — и почему инженерная дисциплина важнее количества промптов*

---

<spoiler title="TL;DR — для нетерпеливых">

**Проблема:** 90% разработчиков используют AI-инструменты как «волшебную кнопку» — бросают промпты наугад и молятся. Это называется vibe coding, и результат предсказуемо плохой.

**Решение (IndyDevDan):** Tactical Agentic Coding — подход, основанный на:
- **Core Four:** Контекст, Модель, Промпт, Инструменты — 4 рычага, которые нужно осознанно настраивать
- **Builder + Validator:** Один агент строит, другой проверяет. Дороже вдвое, надёжнее на порядок
- **Мета-промпты:** Промпт, который создаёт другие промпты. Шаблонизация инженерных решений
- **Самовалидация:** Агент проверяет свою работу хуками до того, как отчитается

**Наш опыт:** 44 агента в Orchestrator Kit используют те же принципы — мы пришли к этому параллельно.

**Репозиторий:** [github.com/maslennikov-ig/claude-code-orchestrator-kit](https://github.com/maslennikov-ig/claude-code-orchestrator-kit)

</spoiler>

## Два лагеря — и пропасть между ними

Я в IT с 2013 года. Последние два года строю AI Dev Team в DNA IT: 54 специалиста + 44 AI-агента. Пишу про агентную разработку регулярно — и каждый раз получаю два типа комментариев:

1. «Это же vibe coding, только с красивой обёрткой»
2. «У нас так уже работает, но мы называем это по-другому»

Оба лагеря ошибаются. И вот почему.

**Vibe coding** — это когда ты бросаешь промпт в ChatGPT/Cursor/Copilot и надеешься, что AI выдаст рабочий код. Иногда выдаёт. Чаще — нет. Ты правишь руками, бросаешь новый промпт, снова правишь. Это не разработка, это лотерея.

**Агентный кодинг** — это когда ты создаёшь инженерную систему из специализированных агентов, каждый из которых знает свою область, проверяет свою работу и координируется с другими. Ты не пишешь код — ты проектируешь систему, которая пишет код.

Разница примерно как между «позвать знакомого помочь с ремонтом» и «нанять бригаду с прорабом, сметой и приёмкой работ».

IndyDevDan (Дэн Зальцман) — один из тех, кто формализовал этот подход. Его методология Tactical Agentic Coding описывает то, к чему мы пришли параллельно, но с другой стороны. И мне хочется разобрать его подход, показать пересечения с нашим — и честно сказать, где мы расходимся.

## Проблема: Slop Engineering

Дэн вводит термин **slop engineering** — и он точнее, чем vibe coding. Slop — это помои. Slop engineering — это когда инженер производит AI-генерированные помои, потому что не контролирует процесс.

Симптомы:
- Промпты наугад: «Сделай мне авторизацию»
- Нет проверки: скопировал ответ, вставил, запустил, «вроде работает»
- Нет специализации: один AI делает всё — от CSS до миграций БД
- Нет плана: каждый промпт — отдельная сессия без контекста

Результат — код, который:
- Работает на демо, ломается в продакшене
- Содержит дыры в безопасности (OWASP Top 10 — привет)
- Невозможно поддерживать, потому что никто не понимает, почему он такой
- Дублирует логику, потому что AI не знает про существующие утилиты

**Знакомо?** Мне — да. Мы через это прошли. Первые два месяца с Claude Code были именно такими, пока не начали строить систему.

## Core Four: Четыре рычага агентного инженера

IndyDevDan предлагает фреймворк **Core Four** — четыре рычага, которые определяют качество работы с AI-агентами:

```
┌─────────────────────────────────────────────────────┐
│                    CORE FOUR                         │
├─────────────┬─────────────┬──────────┬──────────────┤
│   CONTEXT   │    MODEL    │  PROMPT  │    TOOLS     │
│             │             │          │              │
│ Что агент   │ Какой LLM   │ Как      │ Что агент   │
│ знает о     │ выполняет   │ именно   │ может       │
│ задаче      │ работу      │ ставится │ делать      │
│             │             │ задача   │              │
│ • Файлы     │ • Claude    │ • Мета-  │ • Bash      │
│ • История   │ • Sonnet    │   промпт │ • Read/Edit │
│ • Паттерны  │ • Opus      │ • Шаблон │ • Grep/Glob │
│ • Docs      │ • Haiku     │ • ADW    │ • MCP       │
└─────────────┴─────────────┴──────────┴──────────────┘
```

### 1. Context — самый дорогой ресурс

Контекстное окно агента ограничено. Если забить его мусором — качество ответов деградирует. Если не дать достаточно контекста — агент будет галлюцинировать.

**Тактический подход:** Давайте агенту ровно тот контекст, который нужен для конкретной задачи. Не больше, не меньше.

В нашем Orchestrator Kit это реализовано через **изоляцию контекста**:

```
Main Claude Code (Orchestrator)
  │
  ├→ bug-hunter agent     ← видит только код + паттерны ошибок
  ├→ security-scanner     ← видит только поверхность атаки
  ├→ test-writer          ← видит только тестируемый модуль
  └→ deployment-engineer  ← видит только инфраструктуру
```

Каждый субагент получает узкий контекст. Заканчивает — контекст уничтожается. Основной оркестратор остаётся «чистым».

### 2. Model — выбор модели под задачу

Не каждая задача требует Opus. Для grep-а по кодовой базе хватит Haiku. Для сложного рефакторинга — Sonnet. Для архитектурных решений — Opus.

```
# В нашей системе это выглядит так:
subagent_type: "bug-hunter"    # Sonnet — баланс скорости и качества
subagent_type: "code-reviewer" # Opus — нужно глубокое понимание
subagent_type: "dead-code-hunter" # Haiku — паттерн-матчинг, скорость
```

IndyDevDan называет это «right-sizing the model». Мы называем это здравым смыслом, но формализованным.

### 3. Prompt — фундаментальная единица инженерии

Вот тут начинается самое интересное. Цитата IndyDevDan:

> «Промпт — это фундаментальная единица инженерии в эпоху агентов. Один хорошо написанный промпт генерирует десятки и сотни часов продуктивной работы.»

Это не про «напиши мне функцию сортировки». Это про **мета-промпты** — промпты, которые создают другие промпты. Шаблоны инженерных решений, закодированные в текст.

### 4. Tools — руки агента

Агент без инструментов — философ. Агент с инструментами — инженер. Bash, Read, Edit, Grep, MCP-серверы — это его руки. Чем точнее настроены инструменты, тем меньше агент будет «фантазировать» вместо работы.

## Мета-промпт: промпт, который создаёт промпт

Это ключевая идея IndyDevDan, и она стоит отдельного разбора.

**Обычный промпт:**
```
Создай функцию авторизации с JWT-токенами
```

**Мета-промпт (упрощённо):**
```
Ты — архитектор. Твоя задача — создать план реализации.

Формат плана:
1. Список файлов для создания/изменения
2. Для каждого файла: что именно сделать
3. Зависимости между файлами
4. Критерии приёмки (что проверить после)

Задача: Добавить JWT-авторизацию

Контекст проекта:
- Стек: Node.js, Express, TypeScript
- Существующие файлы: [список]
- Паттерн маршрутизации: [пример из проекта]
```

Разница: мета-промпт **учит агента думать как инженер**. Он не говорит «напиши код» — он говорит «спланируй, разбей на задачи, определи зависимости, установи критерии приёмки».

В нашей системе аналог мета-промпта — это **CLAUDE.md**. Файл, который определяет поведение оркестратора:

```markdown
# Execution Pattern

FOR EACH TASK:
1. Read task description
2. GATHER FULL CONTEXT (code + docs + patterns + history)
3. Delegate to subagent OR execute directly (trivial only)
4. VERIFY results (read files + run type-check) — NEVER skip
5. Accept/reject loop (re-delegate if needed)
6. Update task status to completed
7. Run /push patch
8. Move to next task
```

Это тот же мета-промпт, только вшитый в систему. Агент не «вайбит» — он следует протоколу.

## Builder + Validator: двойная стоимость, тройная надёжность

IndyDevDan предлагает разделить агентов на две роли:

```
┌──────────────────────────────────────────────────┐
│                TASK EXECUTION                     │
│                                                   │
│  ┌─────────────┐         ┌──────────────┐        │
│  │   BUILDER   │────────►│  VALIDATOR   │        │
│  │             │         │              │        │
│  │ Пишет код   │         │ Проверяет    │        │
│  │ Создаёт     │         │ Компилирует  │        │
│  │ файлы       │         │ Тестирует    │        │
│  │ Обновляет   │         │ Ревьюит      │        │
│  │ документацию│         │              │        │
│  └─────────────┘         └──────┬───────┘        │
│                                  │                │
│                          ┌──────┴───────┐        │
│                          │   PASSED?    │        │
│                          │              │        │
│                          │  ✅ → Done   │        │
│                          │  ❌ → Retry  │        │
│                          └──────────────┘        │
└──────────────────────────────────────────────────┘
```

**Builder** — агент, который выполняет задачу. Пишет код, обновляет документацию, создаёт конфиги.

**Validator** — агент, который проверяет результат Builder-а. Компилирует, запускает тесты, проверяет наличие файлов.

Да, это удваивает затраты на API. Но разница в надёжности — колоссальная. Builder без Validator-а — это как разработчик без code review. Работает? Иногда. В продакшен пустим? Нет.

### Наш аналог: Orchestrator + Worker + Quality Gate

В Orchestrator Kit мы пришли к похожей, но более гранулярной схеме:

```
Orchestrator (Main Claude Code)
  │
  ├→ Worker (bug-fixer, code-reviewer, test-writer...)
  │     │
  │     └→ Quality Gate: type-check ✅ build ✅ tests ✅
  │
  ├→ Verify results (read modified files)
  │
  └→ Accept / Reject + Re-delegate
```

Разница: у нас Validator — не отдельный агент, а **набор автоматических проверок** (quality gates) + ручная верификация оркестратором. Это дешевле, чем отдельный агент-валидатор, но требует более умного оркестратора.

| Аспект | IndyDevDan | Наш подход |
|--------|-----------|------------|
| Валидация | Отдельный агент (Validator) | Quality gates + оркестратор |
| Стоимость | 2x за каждую задачу | ~1.3x (gates дешевле агента) |
| Гибкость | Высокая — Validator настраивается | Средняя — gates фиксированные |
| Надёжность | Высокая | Высокая (но зависит от gates) |
| Скорость | Медленнее (2 агента) | Быстрее (1 агент + скрипты) |

Честно: если бюджет позволяет — подход IndyDevDan с отдельным Validator-ом надёжнее. Если нужна скорость и экономия — наши quality gates работают не хуже в 90% случаев.

## Самовалидация: агент, который проверяет сам себя

Ещё одна ключевая идея — **closed-loop prompts**. Агент не просто выполняет задачу, он встраивает проверку в процесс выполнения.

IndyDevDan использует для этого хуки — скрипты, которые агент вызывает для проверки:

```bash
# validate_new_file — проверить, что файл создан
validate_new_file() {
  local filepath="$1"
  if [ ! -f "$filepath" ]; then
    echo "FAIL: File $filepath not created"
    return 1
  fi
  echo "PASS: File $filepath exists"
  return 0
}

# validate_file_contains — проверить содержимое
validate_file_contains() {
  local filepath="$1"
  local expected="$2"
  if ! grep -q "$expected" "$filepath"; then
    echo "FAIL: $filepath does not contain '$expected'"
    return 1
  fi
  echo "PASS: Found '$expected' in $filepath"
  return 0
}
```

Агент создаёт файл → вызывает `validate_new_file` → если FAIL, исправляет и пробует снова. Замкнутый цикл.

### У нас: Quality Gates как автоматическая самовалидация

В Orchestrator Kit каждый воркер обязан пройти quality gate перед тем, как отчитаться:

```markdown
# Quality Gate (из CLAUDE.md)

VERIFY results:
  1. Read modified files — убедиться, что изменения корректны
  2. Run type-check   — TypeScript компилируется
  3. Run build        — проект собирается
  4. Run tests        — тесты проходят

NEVER skip verification.
```

Принцип тот же: агент не может сказать «готово», пока не прошёл проверку. Разница — в реализации: у IndyDevDan это bash-хуки, у нас — встроенные команды оркестратора.

## AI Developer Workflows (ADW): главная мысль

Вот ключевая идея, которая объединяет всё:

> **Вместо того чтобы писать код приложения — пишите агентов, которые будут писать этот код.**

IndyDevDan называет это **AI Developer Workflows (ADW)** — рабочие процессы AI-разработчика. Не промпт. Не агент. Workflow — последовательность шагов, где детерминированный код (скрипты, хуки, валидации) объединяется с недетерминированными агентами (LLM).

```
ADW = Детерминированный код + Недетерминированный агент

Пример:
1. [Детерм.] Прочитать список TODO из codebase
2. [Агент]   Приоритизировать и декомпозировать
3. [Детерм.] Создать git branch для каждой задачи
4. [Агент]   Реализовать каждую задачу
5. [Детерм.] Запустить тесты, type-check, lint
6. [Агент]   Исправить ошибки (если есть)
7. [Детерм.] Создать PR, смержить
```

В нашей системе ADW — это **Health Workflows**. Тот же принцип: скрипт запускает сканирование → агент анализирует → скрипт валидирует → агент исправляет → скрипт проверяет.

```bash
# /health-bugs — наш ADW для поиска и исправления багов

Фаза 1: [Детерм.] Запуск bug-hunter → генерация отчёта
Фаза 2: [Агент]   Приоритизация найденных багов
Фаза 3: [Детерм.] Создание plan file для bug-fixer
Фаза 4: [Агент]   Исправление по приоритетам (Critical → High → Medium)
Фаза 5: [Детерм.] Quality gate после каждого фикса
Фаза 6: [Агент]   Повторное сканирование → проверка, что не появились новые баги
```

## Практический пример: как выглядит тактический подход

Задача: Добавить эндпоинт `/api/users` с CRUD-операциями.

### Vibe coding (как делают 90%):

```
Промпт: "Добавь CRUD для users"

Результат:
- Может сработать. Может нет.
- Стиль кода — случайный
- Тесты? Какие тесты?
- Валидация входных данных? Зависит от настроения LLM
- Безопасность? OWASP? Что это?
```

### Tactical Agentic Coding (как должно быть):

```
Шаг 1: Мета-промпт создаёт план
  → router file: src/routes/users.ts
  → service file: src/services/user-service.ts
  → types file: src/types/user.ts
  → tests file: src/__tests__/users.test.ts
  → Зависимости: types → service → router → tests

Шаг 2: Builder создаёт types
  → Validator проверяет: tsc --noEmit ✅

Шаг 3: Builder создаёт service
  → Validator проверяет: tsc ✅, unit tests ✅

Шаг 4: Builder создаёт router
  → Validator проверяет: tsc ✅, integration tests ✅

Шаг 5: Builder создаёт тесты
  → Validator проверяет: coverage > 80% ✅

Шаг 6: Security check
  → SQL injection? ❌ (параметризованные запросы)
  → XSS? ❌ (валидация входных данных)
  → Auth? ✅ (middleware проверки токена)
```

Разница: предсказуемость. Ты **знаешь**, что получишь на выходе. Не надеешься — знаешь.

## Семь уровней промптов: иерархия IndyDevDan

IndyDevDan описывает иерархию из 7 уровней — от простого промпта до самосовершенствующегося мета-промпта:

```
Уровень 1: Простой промпт        → "Напиши функцию сортировки"
Уровень 2: Контекстный промпт    → + файлы проекта, стиль кода
Уровень 3: Шаблонный промпт      → + формат вывода, критерии приёмки
Уровень 4: Мета-промпт           → Промпт, создающий промпты для задач
Уровень 5: ADW                   → Детерм. код + недетерм. агент
Уровень 6: Оркестрация           → Несколько ADW координируются
Уровень 7: Самосовершенствование → Агент улучшает свои промпты
```

Большинство разработчиков застревают на уровне 1-2. Продвинутые доходят до 3. Тактический агентный кодинг начинается с уровня 4.

Наш Orchestrator Kit работает на уровнях 4-6. До уровня 7 (self-improving) мы пока не добрались — и IndyDevDan тоже признаёт, что это пока больше теория, чем практика.

## Где я не согласен с IndyDevDan

Было бы нечестно написать «всё идеально совпадает». Вот где мы расходимся:

### 1. Отдельный Validator — избыточно для большинства задач

Запускать второго агента на проверку каждого файла — дорого и медленно. Для критичных задач (безопасность, миграции БД) — оправдано. Для рутины (обновить README, добавить тип) — нет.

Наш компромисс: quality gates (автоматические скрипты) + верификация оркестратором. Отдельный агент-ревьюер — только для сложных задач.

### 2. «Codebase Singularity» — пока маркетинг

IndyDevDan описывает конечную цель как «codebase, которая шипится сама». Красивая идея, но в реальности мы далеки от этого. AI-агенты отлично справляются с рутиной (80% задач), но архитектурные решения, бизнес-логика и edge cases — всё ещё требуют человека.

### 3. Стоимость входа

Tactical Agentic Coding требует серьёзных инвестиций времени в настройку мета-промптов, хуков, валидаторов. Для соло-разработчика на pet-проекте — overkill. Для команды на production — необходимость.

**Подойдёт:**
- Командам от 2+ разработчиков, работающим с AI-инструментами
- Проектам с CI/CD, где качество кода критично
- Тем, кто устал от «вроде работает» и хочет предсказуемости
- Инженерам, которые готовы инвестировать время в систему

**Не подойдёт:**
- Для pet-проектов и хакатонов — overkill
- Для команд без Claude Code / аналогов — нет инфраструктуры
- Для тех, кто хочет «нажать кнопку и получить результат» — тут нужно думать
