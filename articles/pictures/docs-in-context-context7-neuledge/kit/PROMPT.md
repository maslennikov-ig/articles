# Промт для агента: миграция с чистого Context7 на связку @neuledge (L1) + Context7 (L2)

> Вставь этот промт своему агенту (Claude Code / Codex / Cursor / любой клиент с поддержкой MCP), находясь в директории с твоими проектами. Промт намеренно не завязан на конкретный клиент: где нужны клиент-специфичные команды, агент подберёт их сам по тому, в чём он запущен.

---

**Цель.** В моей директории с кодом несколько проектов, в каждом для документации сейчас подключён только Context7. Замени эту схему на двухуровневую связку: `@neuledge/context` как локальный **L1** (основной, бесплатный, локальный поиск по собранным SQLite-пакетам) + **Context7 free** как **L2-fallback** (только на то, что L1 не покрыл).

**Архитектурные требования (прочитай до начала):**

1. **База @neuledge — ГЛОБАЛЬНАЯ, одна на все проекты.** Пакеты лежат в `~/.context/packages/` и общие для всех проектов. НЕ инициализируй базу в каждом проекте. Сервер @neuledge регистрируется в клиенте один раз, глобально. Per-project — только правка конфигов и правил, не отдельные базы.
2. **Транспорт — MCP для обоих уровней** (и @neuledge, и Context7), не CLI. Причина: fallback тут — редкое событие (один вызов на новую либу), token-экономия CLI несущественна, а MCP даёт zero-config и единообразие. Современные MCP-клиенты с отложенной загрузкой схем инструментов почти убирают старый «налог» на размер промта, так что лишнего MCP-сервера бояться не нужно.
3. **Ничего не ломай вслепую.** Сначала инвентаризация, покажи мне план, и только потом меняй. Каждый шаг, меняющий конфиг или удаляющий что-то, делай идемпотентно и обратимо. Ключи — только из переменных окружения, никогда в трекаемые файлы. Не коммить и не пушь без моего подтверждения — показывай дифф.

---

## Этап 1 — Инвентаризация (только отчёт, без изменений)

- Пройди по всем проектам в директории. Найди везде, где подключён Context7: в `.mcp.json`, `.cursor/mcp.json`, `.vscode/mcp.json`, `claude_desktop_config.json`, конфигах Codex, `CLAUDE.md`, `AGENTS.md`, `.cursorrules`, `.clinerules`, любых MCP-конфигах и в правилах/промптах (`context7`, `upstash`, `resolve-library-id`, `get-library-docs`, `query-docs`, `Context7-only`).
- Собери из реальных lockfile'ов каждого проекта список ключевых прод-зависимостей с точными версиями (`package.json` + lock; если есть Python/иные — тоже). Это нужно для сборки глобального L1-стека.
- Выведи отчёт: где и как подключён Context7, и объединённый дедуплицированный список «библиотека + версия» по всем проектам. **Остановись и покажи мне отчёт перед Этапом 2.**

## Этап 2 — Глобальная установка и сборка L1 (@neuledge)

- Установи `@neuledge/context` глобально (`npm install -g @neuledge/context`).
- Зарегистрируй сервер @neuledge в моём клиенте один раз, глобально (команду регистрации подбери под клиент, в котором ты запущен; для остальных клиентов из инвентаризации подготовь сниппеты конфига).
- Собери глобальный стек из объединённого списка либ Этапа 1:
  - **Реестровые либы** ставятся автоматически при первом запросе; ключевые можешь предзагрузить.
  - **Не-реестровые либы** собери через `context add <источник>`. Прибивай версию к lockfile тегом, где можно (`context add https://github.com/.../tree/vX.Y.Z`), чтобы доки соответствовали реально используемой версии.
  - **Важно по качеству индекса:** если при `context add` ловишь warning о малом числе секций — доки лежат в отдельном репозитории. Найди правильный docs-репо (паттерны `project-docs`, `project.dev`, `project-website`; пример: для React это `reactjs/react.dev`, не `facebook/react`) и/или укажи точный `--path` на папку с доками. Не индексируй весь репо целиком, если доки в подпапке — это раздувает выдачу.
- Покажи `context list` после сборки, чтобы я видел собранный стек.

## Этап 3 — Context7 как L2-fallback (MCP)

- В каждом проекте оставь/добавь Context7 MCP, но переопредели его роль с «основного» на «fallback». Context7 free, ключ из переменной окружения `CONTEXT7_API_KEY` (не хардкодь — бери из env/.env, убедись, что `.env` в `.gitignore`).
- Учти лимит Context7 free: ~1000 запросов/мес + жёсткий rate-limit ~60/час (429). Это L2, срабатывает редко; но если будешь делать залповые проверки при миграции — троттли, чтобы не словить 429.

## Этап 4 — Политика маршрутизации в правилах агента

- В `CLAUDE.md` / `AGENTS.md` / `.cursorrules` каждого проекта замени старую инструкцию «Context7-only» на политику двух уровней (адаптируй под формат каждого файла):
  > При необходимости документации сначала запрашивай через @neuledge (L1, локальный). Если @neuledge не вернул релевантный результат или библиотеки нет в локальном стеке — используй Context7 (L2, fallback). При запросах к @neuledge извлекай доменные термины и имена API (не общие глаголы): поиск там FTS5 + BM25 по ключевым словам, не семантика. Из цепочки вроде `z.string().email()` бери конечный метод (`email`), а не первый.
- Добавь короткую заметку: если регулярно используешь новую либу, которой нет в L1 — добавь её один раз через `context add` и перезапусти сервер @neuledge; тогда она перестанет уходить в fallback.

## Этап 5 — Верификация

- На 1–2 проектах прогони проверку: запрос по либе из локального стека должен обслуживаться @neuledge (быстро, локально); запрос по заведомо отсутствующей либе — уходить в Context7. Покажи, что оба пути работают.
- Выведи итоговую сводку: какие проекты мигрированы, что собрано в глобальном L1, где лежит env-ключ Context7, и список ручных шагов (если остались — например, рестарт MCP-клиента).

---

## Ограничения и поведение

- Не коммить/не пушь без подтверждения — покажи дифф конфигов и правил.
- Не удаляй Context7 полностью — он становится L2, а не исчезает.
- Ключ Context7 — только через env, никогда в трекаемые файлы.
- Если в проекте Context7 подключён не через MCP (CLI или skill) — приведи к MCP-схеме для единообразия, но отметь это в отчёте.
- Любой шаг, который не можешь выполнить сам (например, рестарт MCP-клиента), вынеси в явный список «сделать вручную» в финальной сводке.
