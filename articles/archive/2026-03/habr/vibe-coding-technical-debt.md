# «Оно же работает» — самая дорогая фраза в вайб-кодинге

*Что находят разработчики под капотом проектов, собранных нейросетью за выходные.*

---

Недавно к нам пришёл проект на доработку. Заказчик — малый бизнес, задача понятная: веб-приложение для внутренних процессов, ничего космического. Предыдущий «разработчик» — знакомый знакомого, который собрал всё через Cursor за пару выходных.

Приложение работало. Кнопки нажимались, данные сохранялись, даже дашборд с графиками был. Заказчик показал — я подумал: ну, может, не так уж плохо, допилим. Попросил доступ к репозиторию.

Открыл код. Закрыл. Налил кофе. Открыл снова.

---

## Небольшой контекст

После [прошлой статьи](https://habr.com/ru/articles/1000134/) про AI в разработке мне написали, что я агитирую за вайб-кодинг. Нет. AI — бензопила: лесорубу она помогает, а человеку, который впервые её взял, — отрежет ногу.

Вот что бывает, когда бензопилу дали человеку без инженерного опыта.

---

## Что мы нашли

Начну с того, что **архитектуры не было**. Вообще. Всё приложение — четыре файла. Один из них — `app.js` на 3400 строк, в котором перемешано всё: роутинг, бизнес-логика, запросы к базе, валидация (точнее, её отсутствие), и куски HTML, рендерящиеся прямо в обработчиках запросов. Без шуток. Template literals с HTML внутри `res.send()`.

Знакомый паттерн? Если вы хоть раз работали с легаси, которое писал один человек без ревью — вы узнаете. Только есть нюанс. Легаси, написанное человеком, обычно имеет *внутреннюю логику*. Кривую, странную, но логику. Человек думал, принимал решения, у него был свой стиль. Можно проследить ход мысли: вот тут он торопился, тут не знал лучшего способа, а тут скопировал со Stack Overflow.

У вайб-кода логики нет. Нейросеть генерировала каждый кусок изолированно, в ответ на конкретный промпт. Связность между кусками — случайная. Один обработчик использует `async/await`, соседний — колбэки, третий — промисы. Не потому что автор так решил, а потому что три промпта дали три разных ответа, и никто не подумал привести к единому стилю.

А зачем? Оно же работает.

## Один endpoint. Семь проблем

Вот реальный фрагмент (обезличен, но паттерн сохранён):

```javascript
app.post('/api/login', (req, res) => {
  const { email, password } = req.body;

  db.query(
    `SELECT * FROM users WHERE email = '${email}'
     AND password = '${password}'`,
    (err, rows) => {
      if (rows.length > 0) {
        const token = jwt.sign(
          { id: rows[0].id },
          'super-secret-key-123'
        );
        res.json({ token, user: rows[0] });
      }
    }
  );
});

// Ниже в том же файле:
function authenticateUser_old(email, password) {
  // TODO: implement
  return true;
}

function authenticateUser_v2(email, password) {
  return db.query(
    `SELECT * FROM users WHERE email = '${email}'`
  );
}
```

Считаем:

1. **SQL-инъекция** через конкатенацию строк. Классика. `' OR '1'='1` — и вы внутри.
2. **Пароль хранится и сравнивается в открытом виде.** Ни bcrypt, ни argon2 — ничего. Чистый plaintext в базе.
3. **Секрет JWT захардкожен** прямо в коде. Не в `.env`, не в секрет-менеджере — в строковом литерале.
4. **`res.json({ user: rows[0] })`** — возвращает *всю* запись из таблицы `users`, включая поле `password`.
5. **Нет обработки ошибок.** Если `err` не null — он молча игнорируется. Клиент повиснет без ответа.
6. **Нет ответа при неуспешной аутентификации.** Если `rows.length === 0`, ничего не происходит. HTTP-соединение просто зависнет до таймаута.
7. **Нет rate-limiting.** Brute-force? Пожалуйста, хоть миллион запросов.

А под этим — две мёртвые функции. `authenticateUser_old` с `return true` (видимо, первая попытка, от которой отказались) и `authenticateUser_v2` (вторая попытка, тоже не используется, но с той же SQL-инъекцией). Нейросеть генерировала новые версии, старые оставались. Никто не чистил.

Семь уязвимостей и проблем в одном endpoint из 15 строк. И это авторизация — самое чувствительное место в приложении.

(Для тех, кто скажет «ну, это же надуманный пример» — нет. Это собирательный, но каждая проблема взята из реального кода. OWASP ежегодно публикует Top-10, и SQL-инъекция там стабильно в первой тройке. А вайб-кодеры про OWASP не слышали.)

## Цикл костылей

Вот как это работает. Менеджер или фаундер собирает MVP через AI. Приложение функционирует. Появляется баг.

Человек пишет нейросети: «У меня ошибка X». Нейросеть отвечает: «Извините, сейчас исправлю» — и вместо того чтобы разобраться в причине, наклеивает поверх ещё один слой. Обходной путь. Костыль.

Баг исправлен? Формально — да. Код стал лучше? Нет, он стал *больше*. И хуже.

Через десять таких итераций вы имеете код, в котором одна и та же логика реализована тремя разными способами в трёх разных местах, потому что каждый промпт генерировал решение с нуля, не зная о предыдущих. Через двадцать — вы имеете систему, которую невозможно модифицировать, не сломав что-нибудь ещё.

В нашем случае это было ровно так. Заказчик попросил добавить авторизацию по ролям. Нейросеть добавила проверку `if (user.role === 'admin')` в каждый из тридцати обработчиков. В каждый. Отдельно. Copy-paste тридцать раз. Ни middleware, ни общей функции — буквально копия одного и того же условия в тридцати местах.

А потом заказчик попросил добавить роль «модератор».

## Масштаб проблемы

Это не один проект. Это тренд.

GitClear проанализировали 150 миллионов строк кода и зафиксировали **8-кратный рост дублирования** после массового внедрения AI-инструментов. Механизм простой: человек не рефакторит, а просит нейросеть «дописать ещё кусок». Каждый кусок работает изолированно. Архитектура расползается.

Аналитики Salesforce Ben используют для 2026 года термин «Год технического долга». Компании, которые в 2024–2025 быстро собирали продукты без инженерного контроля, сейчас обнаруживают: системы не масштабируются, падают под нагрузкой, текут данные. И нанимают (дорогие) команды, чтобы расчищать завалы.

HackerNoon опубликовал статью с названием, которое отлично резюмирует ситуацию: «Vibe Coding is a Technical Debt Factory». Вайб-кодинг — фабрика техдолга.

## Правило 80/20

Есть удобная модель, которая объясняет, почему вайб-кодинг *выглядит* как работающее решение. Нейросеть отлично закрывает 80% задачи. Интерфейс, базовый CRUD, типовые формы, стандартный роутинг — всё это генерируется быстро и выглядит прилично. Happy path работает.

Оставшиеся 20% — интеграции со старыми системами, обработка ошибок, безопасность, масштабирование, edge cases — это ядро, которое отличает рабочий продукт от демки. И именно здесь вайб-код ломается.

Нейросеть не умеет думать о том, что произойдёт, когда пользователь введёт emoji в поле «номер телефона». Или когда два пользователя одновременно попытаются изменить одну и ту же запись. Или когда сервер базы данных перезагрузится в момент транзакции. Она генерирует код для сценария «всё идёт по плану». А в реальности так не бывает.

(Кстати, забавное наблюдение: edge cases — это то, на чём строится инженерный опыт. Именно поэтому мидл отличается от джуна. Джун тоже пишет работающий happy-path. А мидл знает двадцать способов, которыми этот happy-path сломается. Нейросеть в этом смысле — вечный джун. Ты ей напиши конкретно, что обработать — обработает. Но сама не предложит.)

## «А что, если я сам так делаю?»

Сейчас кто-нибудь подумает: «Подождите, я тоже использую Cursor / Copilot / Claude Code. Я тоже вайб-кодер?»

Нет. И вот почему.

Есть принципиальная разница между двумя подходами.

Вайб-кодинг — это когда человек без инженерного опыта описывает «хочу вот такое приложение», получает результат и принимает его на веру. Он не понимает, что сгенерировала модель. Не может оценить качество. Не знает, где искать проблемы. Если что-то ломается — единственный инструмент: написать ещё один промпт.

AI-ассистированная разработка — это когда инженер использует модель как инструмент. Он понимает архитектуру. Читает сгенерированный код и видит проблемы. Знает, когда принять результат, а когда переписать. Контролирует процесс, а не плывёт по течению.

Разница — как между человеком, который принимает таблетки по совету нейросети, и врачом, который использует AI для дифференциальной диагностики. В обоих случаях задействован AI. Результат — принципиально разный.

Инструмент не определяет качество. Его определяет тот, кто инструментом пользуется.

Именно это я имел в виду в [прошлой статье](https://habr.com/ru/articles/1000134/), когда писал про AI в разработке. Не «промпт-инженеры заменят программистов», а «инженеры, освоившие AI, будут на голову сильнее тех, кто его игнорирует». Ключевое слово — *инженеры*. Человек с бензопилой — не лесоруб. Лесоруб с бензопилой — лесоруб, который валит деревья быстрее.

И — давайте будем честны — если вы на Хабре, вы скорее всего из категории инженеров. Для вас нейросеть — быстрый помощник, а не замена мышления. И именно поэтому вашу работу вайб-кодеры заменить не могут. Наоборот: чем больше вайб-кода появляется в мире, тем дороже стоит инженерная экспертиза.

## Что делать, если принесут вайб-проект

Практика, к которой многие из нас придут (или уже пришли). Вам отдают проект «на доработку». Открываете — и понимаете, что перед вами вайб-код. Что дальше?

**Сначала — аудит, а не код.** Не бросайтесь сразу рефакторить. Сначала поймите, что вообще работает, а что только *выглядит* как работающее. Прогоните статический анализатор. Запустите тесты. Нет тестов? Ожидаемо. Проверьте хотя бы ключевые сценарии руками.

**Ищите дыры в безопасности первым делом.** SQL-инъекции, XSS, захардкоженные секреты, отсутствие валидации входных данных. В вайб-коде это почти гарантированно есть. Если приложение работает с персональными данными — это не «можно починить потом», это «нужно закрыть прямо сейчас». В реалиях РФ — штрафы за утечку ПДн не шутка.

**Оцените: рефакторить или переписывать.** Иногда рефакторинг дешевле. Иногда — дороже. Эмпирическое правило: если в коде нет архитектуры (всё в одном файле, нет разделения на слои, нет переиспользования), скорее всего проще написать заново, используя существующую логику как ТЗ. Код плохой, но он фиксирует бизнес-логику — а это ценно.

**Объясните заказчику.** Это самое сложное. Человек искренне считает, что у него «почти готовый продукт, нужно только допилить». Он не понимает, почему «допилить» стоит столько же (или больше), сколько сделать с нуля. Объяснять тяжело, но необходимо. Метафора, которая работает: представьте дом, который построили без фундамента. Стены стоят, крыша есть, выглядит нормально. Но надстроить второй этаж нельзя — рухнет.

## Когда вайб-кодинг — ОК

Я не хочу, чтобы статья прочиталась как «всё AI-генерированное — мусор». Это не так.

Вайб-кодинг отлично подходит для прототипов. Проверить гипотезу, показать инвестору, протестировать UX. Для внутренних тулов, которые используют три человека и которым не нужна ни безопасность, ни масштабирование. Для одноразовых скриптов. Для обучения.

Проблема начинается, когда прототип принимают за продукт. Когда «работает на моём ноутбуке» превращается в «деплоим на прод». Когда вокруг MVP, собранного за выходные, строят бизнес с реальными пользователями и реальными данными.

Граница проста: если на кону деньги, данные или репутация — нужен инженер. Человек, который понимает, что происходит под капотом.

## Ирония

Есть в этом ирония. Годами индустрия обсуждала, заменит ли AI программистов. А на практике вайб-кодинг создал больше работы для программистов, а не меньше. Кто-то должен чинить то, что нагенерировали.

На Западе уже появился термин «Vibe Coding Rescue» — целая услуга: аудит, стабилизация и рефакторинг проектов, собранных вайб-кодерами. Звучит нишево, но спрос растёт. Gartner прогнозирует, что к 2028 году 75% enterprise-софта будет содержать AI-сгенерированный код. Кто-то этот код будет поддерживать. И это будете вы.

Нет, подождите. Я перегнул. Не весь AI-код — плохой. Код, сгенерированный опытным разработчиком с помощью AI — это нормальный код. Возможно, даже лучше среднего, потому что модель не делает опечаток и помнит все аргументы API. Проблема конкретно в вайб-кодинге — когда генерацией управляет человек, который не понимает результат.
