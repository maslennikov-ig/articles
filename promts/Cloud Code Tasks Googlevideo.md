Структура статьи (Черновик)
1. Введение: Проблема «Амнезии Агента»
Начните с боли, знакомой всем, кто кодит с AI:

Проблема: Когда вы решаете сложную задачу, контекстное окно быстро заполняется (даже если оно 100k+ токенов).

Следствие: Если начать новую сессию, агент «забывает», что он делал, какие файлы менял и какой был план. Приходится заново скармливать ему контекст или использовать костыли (вроде ручного создания файлов с TODO).

Решение: Раньше сообщество использовало инструменты вроде Beads (запись состояния в JSON). Теперь разработчики Claude Code внедрили нативную систему управления задачами, вдохновленную этим подходом.

2. Что изменилось: Файловая система вместо RAM
Объясните техническую разницу:

Было: TODO-лист хранился в памяти текущей сессии. Закрыл терминал — список пропал.

Стало: Задачи сохраняются локально в папке .claude/tasks.

Это персистентность (сохранение между сессиями).

Задачи имеют ID, описание и зависимости (блокирует/блокируется).

3. Киллер-фича: Зависимости и Суб-агенты
Это самая интересная часть для хабровчан.

Граф зависимостей: Агент теперь понимает, что "Задача 3" не может начаться, пока не выполнена "Задача 2".

Параллелизм: Claude Code может спавнить (создавать) суб-агентов (sub-agents). Если задачи не зависят друг от друга, они могут выполняться параллельно в разных контекстных окнах.

Пример из видео: Автор показывает план рефакторинга, где задачи разбиваются на "волны" (Wave 1, Wave 2). Это экономит токены основного агента и ускоряет работу.

Новые инструменты (Tools): Агентам теперь доступны 4 нативных инструмента:

task_create

task_get

task_update

task_list

4. Практический кейс: Оркестратор и Наблюдатель (Multi-session workflow)
Опишите продвинутый сценарий использования, показанный в видео. Это покажет глубину инструмента.

Общий State: Можно запустить два разных окна терминала с Claude Code, которые смотрят в один и тот же список задач.

Как настроить: Использовать переменную окружения или конфиг для task_list_id.

Сценарий:

Терминал А (Worker): Выполняет задачи, пишет код.

Терминал Б (Checker/Monitor): Работает в фоне. Каждые 30 секунд проверяет выполненные задачи, запускает тесты или ищет уязвимости безопасности. Если находит баг — молча добавляет новую задачу в список для Терминала А.

Почему это круто: Это избавляет от проблемы устаревших данных (stale data), так как синхронизация происходит мгновенно через файловую систему.

5. Настройка и нюансы
Как зафиксировать ID списка задач в settings.json, чтобы он не сбрасывался при команде /clear.

JSON

"task_list_id": "my-project-name"
Предупреждение: Если не задать ID явно, он привязывается к сессии и удаляется при её очистке.
